# ADR 0013: Runs, presets and the run config

Date: 2026-10-07 · Status: Accepted · Requirements: GP-16, GP-21, GP-23, GP-24, GP-25, GP-27, GP-28, SIM-34, SIM-35, SIM-36, NFR-08

## Context

M4 turns the sandbox into roguelite runs ([PROGRESSION_DESIGN.md](../PROGRESSION_DESIGN.md), [M4_PLAN.md](../M4_PLAN.md)). A run is about an hour on a fresh seed: a landless band of ten against a rival warlord's seat, ending in a win, a loss or abandonment. Its start (where the band wakes up, who is in it, the run modifiers and three starting boons) must come from the seed and differ visibly between seeds (GP-27). Several things constrain how runs fit into the existing code:

- **The developed world must not change.** The 2048-tile world carries every M1-M3 test, the benchmarks and the stress mode (M4_PLAN default 6).
- **Runs must replay exactly** (NFR-08), including the player's picks, and replays of the M2/M3 scenarios must keep working.
- **`HeadlessConfig` and `Scenario` are `Copy`,** and the CLI, tests and `record_replay` rely on that.
- **The sim has to stop when a run ends,** although the game and the headless loop keep stepping it.
- **A latent bug (guide G1).** `setup_battle` wrote *player* commands before tick 0. They were recorded, and `verify_replay` re-ran the setup and replayed the log, so they applied twice.

## Decision

- **A run is a seed plus a `RunConfig`** (`sim_core::run`). For now the config holds only a `Difficulty`; M6 adds origins and unlocks. It is `Copy + Eq + Default`, so `Scenario::Run(RunConfig)` keeps `Scenario` and `HeadlessConfig` `Copy`. It travels in the replay header (`Replay.run`, `#[serde(default)]`), and `REPLAY_FORMAT` went from 4 to 5 once. The difficulty selects data, never RNG streams.
- **`RunState` is one resource, always present and hashed.** It holds `config: Option<RunConfig>` (`None` means no run, as in the developed world), a `pending` outcome, the final `outcome`, its `cause` and `ended_at`. `Offers`, `Chronicle`, `FactionModifiers` and `RunProgress` are always present too, with defaults outside a run, so the coverage test and saves see them from tick 0.
- **The run gate.** All nine `SimSet`s run only while `run_in_progress` holds. A serial step ends a run with `RunState::finish(outcome, cause)`: the first caller in a tick wins, and outside a run the call does nothing. `settle_outcome` (in `BookkeepingSet::Record`, after `record_events`) makes the outcome final and records `RunEnded`. The ending tick completes; every later tick is a no-op, so `SimTick` and the state hash freeze and commands are no longer consumed. Frontends keep stepping and need no special case.
- **Two presets in one `worldgen.ron`.** The file holds two complete settings blocks, `developed` and `run`. `WorldGenSettings::default_data()` stays the developed world. The run preset is a 1024-tile island with 4 regions and about 25 settlements. Only the run preset draws settlement sizes and places monuments; developed has `monuments.per_region: 0` and no size tiers. The developed world therefore generates the same terrain, settlements and roads as before and spawns no new entities.
- **Every run settlement is populated at a drawn size.** Tier counts are apportioned by weight (largest remainder), shuffled over the settlements, and each settlement's people are drawn uniformly within its tier, all from one new stream. The largest becomes the rival's seat, the unique largest at 450 or more. `populate` has a size mode keyed on `SettlementSize`; without sizes it runs the M2 path unchanged.
- **Monuments are placed by worldgen in step 1** (GP-23 placement), because the start needs to count them. Each region draws its kinds by weight. Each slot takes the suitable tile nearest a seeded anchor, under data-driven site rules. Monuments sit at least 52 tiles from every settlement centre (beyond the 45-tile threat radius, so a guard camp never frightens a village) and, where possible, `min_spacing` (40) tiles from each other: if no kind fits a slot, the spacing is relaxed to a half and then a quarter, and a slot nothing fits stays empty (none of seeds 1-20 needed it). Holders, guards and bonuses come in step 4; they must not assume monuments are 40 tiles apart, and should use the actual distances between them.
- **The start draws are a pure function,** `draw_start(seed, &Progression, &RunWorld)`, of the seed, the data and the generated world. The seat is the largest settlement. A start tile is open ground at least 40 tiles from every settlement and reachable on foot from the seat. The band starts in the region farthest from the seat (by settlement centroid) that has such a tile with 2-3 monuments within `monument_radius`, or else in the farthest region. Tiles are ranked by class (monument count, then the side away from the seat, then the drawn kind of ground, then the region's edge); within the best class, distance from the seat plus seeded jitter decides. The band template, the champion's trait, one or two run modifiers (no two from one group) and three distinct start boons are drawn, each from its own new stream at tick 0. With no App involved, a test can check twenty seeds in about ten seconds.
- **Setup is shared and writes no player commands.** `sim_headless::set_up_scenario` is the one setup path for headless runs, tests and `game_app`. Before tick 0, `setup_run` seats the player at the start, spawns the band and its champion (with one trait), applies one-off modifiers, posts the start offer and records `RunStarted`, all by editing state directly. Setup that needs orders writes `SimCommand::ai`, which is never recorded; `setup_battle` now does, which fixes G1.
- **Offers live in sim_core, and picks are commands.** `Offers` is hashed in sim_core, so the UI, saves and progression can read it without depending on sim_military. A pick is a recorded player command, `ChooseOffer { offer, choice }`, applied in `orders::apply` like every other command. The first pick takes the offer, so a second one (a double click) is refused as "no such offer". `AbandonRun` works the same way, and only the player may abandon.
- **The sim's own AI has its own input sub-set.** `SimInputSet::Ai` runs between `Inject` and `Consume`, so scripted or recorded commands and AI commands always arrive in the same order. Raiders moved there; the rival joins in step 7.
- **Run-only rules leave the developed world alone** (guide D6):
  - they are gated by `in_run`;
  - new draws use new stream keys;
  - outside the run preset, no entity is spawned before the villagers;
  - multipliers are exact no-ops at 1.0.

## Consequences

- **The developed world is unchanged.** `sim_headless --seed 42 --ticks 1200 --stats-every 600` prints the same terrain mix, settlements, roads and village statistics as before M4. Only the state hash differs: there are new hashed resources, and `WorldGenSettings` is hashed as its RON text. No golden hashes existed.
- **Skirmish and battle hashes changed.** `raiders::think` now runs after scripted input, battle setup orders are AI commands (so `--battle` replays log two fewer commands), and `sample_orders` draws from a wider range that includes offer picks and refused abandons. The M3 tests pass unchanged.
- **Format-4 replays are refused.** None were checked in.
- **The run island is cheap.** It has about 4,000-4,700 people. A tick costs about 1 ms in release, and setup about 0.5 s.
- **Start terrain leans to the coast** (12 of seeds 1-20), because the ranking puts the monument count and the side away from the rival before the drawn kind. `start.terrain_weights` and the ranking can be retuned; nothing depends on the current draws.
- **A run that ends logs fewer commands than its script.** The gate stops consuming commands, so its `RunResult.log` is shorter than the scripted list.
- **Tests:**
  - `run_start`: 20 seeds checked at world level, plus same-seed identity, the boon picked once, and abandoning.
  - `run_state_hash_covers_every_sim_component`, which every later M4 step extends with its state.
  - `a_run_replays`.
- **Events infrastructure landed with this step** (`SimEvent`, `Chronicle`, `EventFeed`, sorted recording), so later steps can report as they go. Its design is recorded with the chronicle in step 9.

## Addendum: dominion boons and captain slots (M4 step 5, GP-24, GP-25)

- **Dominion is tallied, not tracked.** Once a game hour, in a run, slot 8 of the progress driver (`progression::dominion::tally`) sums each region's people (`SettlementEconomy.population`, settlements in SpawnId order, `NO_REGION` left out) and the part in settlements the player owns into `RunProgress.dominion` (one `RegionTally {total, held_by_player, flags}` per region, `WorldMap::region_count` of them). No event drives it, so conquest, invitations, revolts, recruiting and deaths are all counted the same way.
- **One offer per threshold and region, for the whole run.** The first time a region's share reaches a progression.ron `dominion.thresholds` entry (25%, 50%; compared exactly, in f64), its bit in `flags` is set and a `DominionBoon {region, step}` offer is posted. Flags are never cleared, so losing land and taking it back offers nothing new, and boons are kept even if the land is lost (PROGRESSION_DESIGN open question 2). An hour that crosses both thresholds posts both offers, region by region, then step by step.
- **The offer reflects the holdings.** Three distinct Dominion boons are drawn without replacement, each weighted `weight x (1 + sum(w x amount))` over its optional `favour` list: farms and a smithy in the region's player-owned settlements, owning the region's most populous settlement, `Battle` chronicle entries (from step 6), enemies killed. The draw uses stream `sim_military::progression::boons ^ offer id` at the posting tick; the start offer (id 0) drew from `boons ^ 0` at tick 0, so no two offers share a stream. Picked boons may be offered again later and stack.
- **Captain slots come from the land.** `sim_military::captain_slots(world, faction)` is `Some` only in a run and for the player: `min(cap, max(first_village_slots once a settlement is held, floor(people held / per_captain)) + CaptainSlots(n) boons + floor(the flat CaptainSlots modifier))`, never below 0 (8, 300 and 1 shipped). `orders::appoint` keeps army.ron `max_captains` (9, the champion counted) as the hard limit and, in a run, refuses with "no captain slot" once the player's captains other than the champion fill the slots. Outside a run, and for any other faction, the old rule alone applies, so skirmish appointments (and `sample_orders`) are unchanged. Successions (`casualties`' `succeed`) make captains without a slot check. Slot boons are a dedicated `Effect::CaptainSlots(n)`, read from `RunProgress.boons` at the moment of the check, so a pick counts at once rather than at the next hourly modifier rebuild; `Stat::CaptainSlots` stays for traits and future sources.
- **The UI reads a stored copy.** `RunProgress.captain_slots` is refreshed after the hourly modifier rebuild (`dominion::refresh_slots`, right after slot 10) and after every boon pick; `AppointCaptain` always checks the live value, so a settlement won mid-hour counts at once.
- **Consequences.** `--run` replays' random `AppointCaptain`s are now mostly refused (no land at the start); skirmish and developed are unaffected. `RunProgress` hashes the tally and the slots. Tests: `dominion` (tests/tests/dominion.rs: crossing, picking, losing and re-crossing 25%, 50%, slots by the formula, refusals, the cap) and the dominion.rs unit tests (the slot formula, weighting, the exact threshold comparison).

## Addendum: champion, traits, veterans and succession (M4 step 6, SIM-34, SIM-35, SIM-36)

- **A battle belongs to one army.** Every landed blow (`resolve_strikes`) marks striker and victim with `Veteran.fought` and stamps both armies' captains: `battle_since` (first blow) and `last_engaged` (latest). The hourly `veterans::end_battles` (slot 1 of the progress driver, every preset) ends a battle once no blow has landed for army.ron `veterans.quiet_hours` (1): every living member who fought counts one battle, `fought` is cleared, and a `Battle` event reports the army's faction, captain, head count and `battle_losses` (counted in `casualties`). The state lives in `Captain`, so an heir carries it on. Battle events with the player's faction feed the dominion `Battles` holding.
- **Ranks are run-only and derived.** In a run, a survivor's rank is the number of `veterans.thresholds` (1, 3, 6) that `battles x (1 + VeteranRate)` reaches, never lower than before; outside a run ranks stay 0, so skirmish and battle numbers are byte-identical to before. "Hardened" (+25%) needs no randomness: 5 battles count as 6.25. Each rank's gains are its total, applied at the use site and only for rank > 0: attack and defence points in `resolve_strikes`, morale on the target and a share off the desertion chance in `soldier_upkeep`. With the step, `Stat::Desertion` (desertion chance), `Stat::RecruitChance` (each villager's chance in `recruit`) and `Stat::VeteranRate` gained their consumers, all exact no-ops at 1.0, so every trait and boon effect now acts.
- **The champion ranks by deeds, credited where they happen.** `champion::credit(world, faction, feat)` adds progression.ron `champion.points` to the faction's champion's `ChampionRank`: a battle its own army lived through (`end_battles`), a monument the faction took (`monuments::hold`), a settlement conquered or invited into (`transfer_seeded`), a request answered (`requests::complete`). Ranks follow at the hourly `champion::rank_ups` (slot 9): each rank reached posts its own offer of three distinct traits from `champion_traits`, new ones first, all of an hour's offers drawn in turn from one stream, `sim_military::progression::traits ^ champion` at that tick (the start trait used `traits ^ 0` at tick 0; a champion's SpawnId is never 0). A pick joins `Traits`; its effects arrive with the next hourly modifier rebuild, like every other modifier.
- **Succession is decided in `casualties`, before `succeed`.** The champion marker, `ChampionRank` and `Traits` live on the person, not in `Captain`, so `succeed` handing the fallen's army to its first follower never makes that follower champion. Candidates are the faction's other living captains, ordered by champion rank, then veteran rank, then SpawnId. Once a run (`RunProgress.succession_used`) the first becomes champion with the rank, the points, the first half of the traits (rounded down, pick order) and any trait offer still waiting; otherwise the run ends `Lost` with `Cause::Death { faction }` (the striker's faction from `Casualties::slain_by`), or `Cause::Starvation`. `ChampionFell` is reported either way.
- **Consequences.** Hashes change everywhere (army.ron text, `Veteran` and `ChampionRank` registered, the captain's battle fields); developed, skirmish and battle stdout are unchanged. Soldier triggers for traits (a captain who routs becoming Shaken) are not in M4: traits come only from the champion's start and ranks. Tests: `champion` (tests/tests/champion.rs), the veterans.rs and champion.rs unit tests, and the run coverage test, whose assault now ends a battle.

## Addendum: the rival and the pacing director (M4 step 7, GP-28, GP-16)

- **The rival is scripted, on data.** progression.ron `rival` has one row per difficulty (the run's `RunConfig` picks it; the difficulty selects data, never streams). `setup_run` seats the rival at its seat, hands it every populated settlement of the seat's region through `set_owner` (quietly: no `Conquest` events, no conquest counts) with loyalty `start_loyalty`, and spawns its garrison at the seat with a standing `Garrison` order, after the band and the guard camps, so earlier SpawnIds are unchanged. Its clock (`rival::clock`, slot 11 of the progress driver) runs while it holds its seat: the seat's defence bonus steps up by day (added to the rival's `Defence` multiplier near the seat in `resolve_strikes`, standing in for walls until M5), levies enlist its own villagers with `enlist_into` (they walk in from its lands), and raids split a band off the garrison (`orders::split_army`, extracted from `AppointCaptain`, so a raid weakens the seat). The stronger and weaker rival modifiers (`RivalStrength`) scale the garrison, levies and defence. Raiding bands carry a hashed `RivalBand`, passed on to the heir when the captain falls, and are steered by `rival::think` in `SimInputSet::Ai` after `raiders::think`, with AI-origin commands; a band re-issues orders only when its target changes, so an attack in progress isn't reset. Taking the seat wins the run (`transfer_seeded`) and frees the rest of the rival's lands.
- **The director keeps the run from going quiet.** director.ron holds one personality per difficulty; `director::step` (slot 12, last) measures tension from hashed state and brings a raider band when the next hourly check would pass `quiet_limit_hours` without a notable event (`Chronicle::last_notable`), when the first event (`director::eventful`: a request, raiders, a raid, a fight) hasn't come by `first_event_within_hours`, or when tension is below zero with `spacing_hours` (paced by restless roads) passed and fewer than `max_bands` roaming. So the quiet limit is a guarantee, not a target. A band (stream `sim_military::director` at the tick) appears around the village nearest the champion and raids it first (its `Raider.target`, hashed), which makes the village ask the player to drive it off: the director nudges requests through the sim rather than inventing them.
- **Raiders in a run prey on the player only, and only on what they can beat.** They hunt the player's armies no bigger than themselves and raid only the player's settlements; with nothing of the player's to raid they hunt when hungry. Outside a run nothing changed (skirmish and battle output identical).
- **The bot is a player.** `sim_headless::bot` reads the world between ticks with SpawnId-sorted queries and sends ordinary player commands every game hour, so a bot run records and replays like any other (`--run --bot --record`). The step-7 bot is a skeleton (offers, food requests, foraging, monuments); step 11 makes it win. `sim_headless::step_until_event` is the headless fast-forward.
- **Consequences.** Hashes change everywhere (new hashed resources, the raider's target); developed, skirmish and battle stdout are byte-identical. `sim_headless --commands` in a run now orders only the player's captains. Tests: `rival` (tests/tests/rival.rs), `director` (tests/tests/director.rs), the rival.rs and director.rs unit tests, and the run coverage test, which moves the rival's first levy and raid forward.
